HPC Parallel File System & High-Speed Storage

A. Project Overview

Problem Statement

Conventional NFS storage uses a single (or small number of) server(s) to serve all clients, which becomes a severe bottleneck when hundreds of HPC compute nodes need to read/write large datasets simultaneously — the storage system itself, not the compute, ends up limiting job performance.

Proposed Solution

A parallel file system (Lustre or BeeGFS) that stripes data across many storage servers and targets simultaneously, allowing aggregate throughput to scale with the number of storage nodes, connected via RDMA networking (InfiniBand or RoCE over 100GbE) to minimize latency, with NVMe/SSD used as a caching tier for frequently accessed data.

Objectives

  • Deploy a parallel file system capable of serving high concurrent I/O from many compute nodes.
  • Use NVMe/SSD caching to accelerate hot data access.
  • Leverage RDMA networking (InfiniBand/100GbE) to minimize I/O latency.
  • Benchmark and validate achieved throughput against HPC workload requirements.

Intended Users

HPC compute clusters (Project 04), AI training clusters (Project 02), and any workload requiring very high aggregate storage throughput.

B. Business Value

Operational BenefitsEliminates the storage bottleneck pattern common with single-server NFS under heavy concurrent HPC access.
Cost OptimizationHigher upfront cost than simple NFS storage, justified when compute cluster scale makes storage I/O the limiting factor on overall cluster utilization.
ProductivityFaster data access directly translates to shorter job completion times for I/O-intensive HPC/AI workloads.
ScalabilityThroughput scales near-linearly by adding more storage server/target nodes, unlike single-server NFS.
Security & ReliabilityAccess control integrated with the same centralized identity used across the HPC cluster.
Organizational ImpactA deliberate complement to the general-purpose Ceph storage platform (Project 12) — this system is specifically for raw HPC I/O performance, not general file sharing.

C. Technical Architecture

Architecture Overview

A parallel file system architecture with metadata servers (handling file/directory metadata) separated from object storage servers (handling actual data), allowing both metadata operations and data throughput to scale independently, striped across many storage targets accessed concurrently.

graph LR U[User / Client] --> GW[Application / Gateway Layer] GW --> CORE[HPC Parallel File System & H Core Services] CORE --> DATA[(Data / Storage Layer)] CORE --> MON[Monitoring & Observability] MON --> ADMIN[Administrator]

Components

  • Metadata Server(s) (MDS/MGS in Lustre terms)
  • Object Storage Servers / Storage Nodes (OSS in Lustre terms, storage servers in BeeGFS)
  • NVMe/SSD caching tier
  • RDMA network fabric (InfiniBand or RoCE/100GbE)
  • IOR benchmarking suite for validation

Data Flow

Compute node issues a file I/O request → metadata server resolves file layout/striping information → compute node communicates directly and in parallel with multiple storage servers/targets for the actual data transfer → RDMA networking allows this to happen with minimal CPU overhead and latency.

Integration Architecture

Mounted directly by HPC cluster compute nodes (Project 04) and AI training cluster nodes (Project 02) as their primary high-performance working storage, distinct from the general-purpose Ceph platform used for other storage needs.

Technology Comparison: Lustre and BeeGFS differ from conventional NFS storage in a fundamental way: NFS serves all clients from a single server (or a small HA pair), creating a throughput ceiling, while Lustre and BeeGFS stripe data across many independent storage servers so that aggregate throughput scales with the number of servers added. BeeGFS is generally considered simpler to deploy and administer; Lustre has a longer track record at the largest supercomputing scales. Both require RDMA-capable networking to realize their full performance potential, which NFS does not typically demand.

D. Technology Stack & Rationale

TechnologyWhy It Was Selected
LustreThe most widely deployed parallel file system in large-scale HPC/supercomputing environments, with a long track record at extreme scale.
BeeGFSGenerally simpler to deploy and manage than Lustre while still providing strong parallel I/O performance, often preferred for mid-scale deployments.
RDMA (InfiniBand/RoCE)Essential for parallel file systems to achieve their full performance potential, since standard TCP/IP networking overhead would otherwise limit achievable throughput and latency.
NVMe/SSD cachingAccelerates access to frequently-used ('hot') datasets without requiring the entire filesystem capacity to be built on the most expensive storage media.

E. Hardware Requirements

CPUModerate CPU requirements on storage servers; metadata servers benefit from strong single-thread performance for metadata operation latency.
GPUNot applicable.
RAMSubstantial RAM on metadata servers for caching file system metadata; storage servers benefit from RAM for data caching.
StorageNVMe/SSD for caching/hot tier; high-capacity HDD or SSD arrays for the bulk capacity tier, striped across many storage targets.
NetworkingRDMA-capable network fabric (InfiniBand or 100GbE with RoCE) is effectively mandatory to realize the performance benefits of a parallel file system.
Recommended ConfigurationMinimum practical deployment: dedicated metadata server(s) plus multiple storage server nodes; scales by adding storage servers for both capacity and throughput.
Estimated, not tested: Achieved throughput is highly dependent on network fabric, storage media and node count; IOR benchmarking against the specific deployment is required for validated figures.

H. Security & Reliability

AuthenticationIntegrated with the HPC cluster's centralized identity for client access control.
AuthorizationDirectory/file-level POSIX permissions, consistent with standard HPC storage access models.
Network SecurityStorage fabric isolated on its own RDMA network segment, separate from general management traffic.
BackupGiven this is typically scratch/working storage, backup policy often differs from archival storage — data is commonly expected to be copied to longer-term storage (Project 12/14) rather than relied upon as permanent.
MonitoringStorage server health and throughput monitoring integrated with the HPC monitoring platform.
Disaster RecoveryDocumented procedure for metadata/storage server recovery; data durability strategy should be explicit given parallel filesystems often prioritize performance over long-term redundancy.
High AvailabilityMetadata server redundancy (where supported) to avoid a single point of failure for the entire filesystem.

I. Testing & Validation

  • IOR benchmark test: validate aggregate read/write throughput against target performance goals.
  • Metadata performance test: measure file creation/stat operation rates under concurrent load.
  • Failover test: validate behavior when a storage server becomes unavailable (data availability depends on configured redundancy).
  • Integration test: confirm HPC/AI cluster compute nodes can mount and use the filesystem under real job workloads.
Test scenarios describe planned validation criteria for this project's current status (Concept). No completed test results are claimed here.

J. Deliverables

  • Operational parallel file system integrated with HPC/AI compute clusters.
  • IOR benchmark report validating achieved throughput and latency.
  • Documented capacity planning and data lifecycle policy (scratch vs archival).
  • Monitoring dashboards for storage server health.

K. Future Enhancements

  • Automated data lifecycle management moving cold data to the Ceph platform (Project 12) or backup system (Project 14).
  • Expansion of the NVMe caching tier as hot-data working sets grow.
  • Evaluation of newer parallel filesystem technologies as they mature.
