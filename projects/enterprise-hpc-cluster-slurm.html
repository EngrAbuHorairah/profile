Enterprise HPC Cluster with Slurm Workload Manager

A centralized, multi-user HPC computing cluster with Slurm-based job scheduling, shared storage and centralized authentication for research and engineering workloads.

A. Project Overview

Problem Statement

Research and engineering teams often rely on individually-owned workstations for compute-intensive work, leading to poor resource utilization, no fair-share policy, and no centralized job history or accounting.

Proposed Solution

A Slurm-managed cluster with dedicated head (controller), login, and compute nodes, shared storage via NFS, centralized identity via FreeIPA/LDAP, and software environments managed through Spack for reproducibility.

Objectives

  • Deploy a head/login/compute node HPC architecture.
  • Implement Slurm-based job scheduling with partitions and queues.
  • Provide centralized authentication and user accounting.
  • Support CPU and GPU resource allocation per job.

Intended Users

Research scientists, engineering simulation teams, and any group needing shared, scheduled access to compute resources.

C. Technical Architecture

Architecture Overview

Classic HPC topology: a controller node runs the Slurm scheduler, login nodes provide user access points, and compute nodes execute scheduled jobs, all sharing a common filesystem and identity service.

graph LR U[User / Client] --> GW[Application / Gateway Layer] GW --> CORE[Enterprise HPC Cluster with Core Services] CORE --> DATA[(Data / Storage Layer)] CORE --> MON[Monitoring & Observability] MON --> ADMIN[Administrator]

Components

  • Slurm controller (slurmctld)
  • Login node(s)
  • Compute nodes (slurmd)
  • Munge for authentication between nodes
  • NFS shared storage for home directories and software
  • FreeIPA/LDAP for centralized identity
  • Spack for software environment management

Data Flow

User logs into login node → submits job via Slurm CLI → slurmctld schedules job to available compute node(s) based on partition/queue policy and requested resources → job executes with access to shared NFS storage → results returned to user's home directory.

Integration Architecture

Spack-managed software stacks allow consistent application environments across all compute nodes without manual per-node installation.

D. Technology Stack & Rationale

TechnologyWhy It Was Selected
SlurmIndustry-standard HPC workload manager with mature support for partitions, fair-share scheduling, and GPU/CPU resource allocation.
MungeLightweight authentication mechanism required by Slurm for secure inter-node communication.
FreeIPA/LDAPCentralizes user/group identity across all cluster nodes instead of managing local accounts per machine.
SpackPurpose-built HPC package manager that handles complex scientific software dependency trees and multiple compiler/library versions cleanly.
NFSSimple, well-understood shared storage suitable for home directories and moderate-scale shared software/data access.

E. Hardware Requirements

CPUMulti-core server CPUs on compute nodes sized to anticipated job parallelism (e.g. 32–128 cores per node).
GPUOptional NVIDIA GPUs on select compute nodes for GPU-accelerated jobs.
RAMSized per expected per-job memory needs; 128GB–512GB per compute node is a common range for mixed workloads.
StorageNFS server with sufficient capacity and IOPS for home directories and shared application installs.
Networking1GbE/10GbE minimum; higher-bandwidth low-latency interconnect (InfiniBand/RoCE) recommended for MPI-heavy workloads (see Project 10).
Recommended ConfigurationMinimum viable cluster: 1 controller/login node + 2–4 compute nodes; production clusters scale to many more nodes.
Estimated, not tested: These are planning-stage sizing estimates; actual requirements should be validated against target workloads before procurement.

H. Security & Reliability

AuthenticationCentralized via FreeIPA/LDAP; no local-only accounts on compute nodes.
AuthorizationSlurm partitions and QoS policies enforce per-group/user resource limits.
Network SecurityCluster internal network isolated from general office network where practical.
BackupRegular backup of NFS home directories and the Slurm accounting database.
MonitoringNode health and job queue monitoring via Grafana.
Disaster RecoveryDocumented rebuild procedure for the controller node and restoration of accounting data.
High AvailabilityOptional secondary Slurm controller for environments requiring scheduler high availability.

I. Testing & Validation

  • Scheduling test: verify jobs are correctly queued and dispatched per partition policy.
  • Resource limit test: confirm per-user/group quotas are enforced.
  • Failover test: validate behavior when a compute node goes offline mid-job.
  • Software environment test: verify Spack-built applications run identically across all compute nodes.
