Enterprise Private AI Platform

A secure, on-premises AI platform providing private LLM inference, retrieval-augmented generation and document intelligence without dependency on external cloud providers.

A. Project Overview

Problem Statement

Organizations handling sensitive data (research, legal, engineering IP) increasingly want LLM-based productivity tools, but public cloud AI services require sending data outside the organization's security boundary, which is unacceptable for regulated or IP-sensitive workloads.

Proposed Solution

A self-hosted stack combining a GPU inference engine (vLLM/Ollama), a vector database (Qdrant) for document retrieval, PostgreSQL for application state, and a FastAPI backend exposing OpenAI-compatible endpoints, fronted by an Open WebUI interface, all running in containers on-premises.

Objectives

  • Provide private large-language-model inference with no external API dependency.
  • Enable retrieval-augmented generation (RAG) over an organization's internal documents.
  • Support multiple concurrent users with role-based access control.
  • Give administrators visibility into GPU utilization and model performance.

Intended Users

Internal engineering and research teams, legal/compliance staff handling confidential documents, and IT administrators managing model deployment.

B. Business Value

Operational BenefitsEliminates per-seat/per-token SaaS AI subscriptions and keeps all prompts and documents inside the corporate network boundary.
Cost OptimizationUpfront GPU hardware investment is offset over time versus recurring API costs at scale; exact break-even depends on usage volume and should be modeled per deployment.
ProductivityGives staff a ChatGPT-like assistant integrated with internal knowledge bases, reducing time spent searching documentation.
ScalabilityAdditional GPU nodes can be added behind a load balancer as user count grows; model size can scale from 7B to 70B+ parameter classes depending on available VRAM.
Security & ReliabilityAll inference and document data stays within the organization's network; access is gated by role-based authentication.
Organizational ImpactPositions IT as an enabler of safe AI adoption rather than a blocker, while retaining governance over what data the model can see.

C. Technical Architecture

Architecture Overview

A three-tier architecture: a presentation tier (Open WebUI), an application/API tier (FastAPI + authentication), and an inference/data tier (vLLM on GPU nodes, Qdrant vector store, PostgreSQL).

graph LR U[User / Client] --> GW[Application / Gateway Layer] GW --> CORE[Enterprise Private AI Platfo Core Services] CORE --> DATA[(Data / Storage Layer)] CORE --> MON[Monitoring & Observability] MON --> ADMIN[Administrator]

Components

  • Open WebUI (chat frontend)
  • FastAPI gateway (auth, routing, rate limiting)
  • vLLM / Ollama inference engine on CUDA GPUs
  • Qdrant vector database for embeddings
  • PostgreSQL for users, sessions, conversation history
  • Document ingestion pipeline (chunking + embedding)

Data Flow

User query → FastAPI gateway → embedding model converts query → Qdrant similarity search retrieves relevant document chunks → context + query sent to vLLM-served LLM → response streamed back through gateway to Open WebUI.

Integration Architecture

OpenAI-compatible API surface allows internal tools (scripts, IDE plugins, internal apps) to call the private model the same way they would call a public API, minimizing integration friction.

D. Technology Stack & Rationale

TechnologyWhy It Was Selected
vLLMHigh-throughput GPU inference engine with continuous batching, giving better concurrent-user performance than naive model serving.
QdrantPurpose-built vector database with filtering support, needed for accurate RAG retrieval over internal documents.
FastAPILightweight, async-capable Python framework well suited to building an OpenAI-compatible gateway with authentication middleware.
Docker/PodmanContainerization isolates each service (inference, DB, vector store) and simplifies reproducible deployment and upgrades.
PostgreSQLMature relational database for user accounts, audit logs and conversation metadata.

E. Hardware Requirements

CPU16+ core server-grade CPU for the application/orchestration tier (model inference is GPU-bound).
GPUOne or more NVIDIA GPUs with 24GB+ VRAM for 7B–13B models; 48GB+ or multi-GPU for 30B–70B class models.
RAM64GB+ system RAM recommended for host OS, container overhead, and embedding caches.
StorageNVMe SSD for model weights and vector index (model weights alone can range from 15GB–150GB depending on model size).
Networking1GbE minimum for internal access; 10GbE recommended if serving many concurrent users or multiple GPU nodes.
Recommended ConfigurationDual-GPU workstation or single GPU server node for pilot deployments; scales to multi-node with a load balancer for production.
Estimated, not tested: All figures are estimated sizing guidance based on published vendor/model requirements, not benchmarked results from a live deployment.

H. Security & Reliability

AuthenticationRole-based login via the gateway, integrable with existing LDAP/Active Directory/FreeIPA.
AuthorizationPer-role access to specific knowledge bases and models.
Network SecurityService exposed only on internal network segments; no public internet exposure by default.
BackupRegular backups of PostgreSQL metadata and the Qdrant vector index.
MonitoringCentralized logging of queries and access for audit purposes.
Disaster RecoveryDocumented restore procedure for model weights, vector index and database snapshots.
High AvailabilityOptional multi-node inference with load balancing for environments requiring high availability.

I. Testing & Validation

  • Functional test: verify RAG responses correctly cite ingested internal documents.
  • Load test: measure concurrent-user response latency at defined token-per-second targets.
  • Security test: confirm unauthorized roles cannot query restricted knowledge bases.
  • Failover test: validate graceful degradation if a GPU node becomes unavailable.
Test scenarios describe planned validation criteria for this project's current status (Concept). No completed test results are claimed here.
