A. Project Overview

Problem Statement

Without centralized monitoring, HPC administrators lack visibility into which jobs are consuming resources, whether nodes are healthy, and where bottlenecks occur — making both troubleshooting and capacity planning guesswork.

Proposed Solution

A Prometheus + Grafana stack with purpose-built exporters (Node Exporter for system metrics, DCGM Exporter for GPU telemetry, Slurm Exporter for scheduler state) and Loki for log aggregation, presenting unified dashboards for cluster-wide and per-job visibility.

Objectives

  • Monitor CPU, GPU, RAM, storage and network utilization across all cluster nodes.
  • Track Slurm job queue status and per-user/group utilization.
  • Provide historical analytics for capacity planning.
  • Alert administrators on cluster health anomalies.

Intended Users

HPC/cluster administrators, infrastructure managers, and capacity planning stakeholders.

C. Technical Architecture

Architecture Overview

Exporters run on every node, scraped by a central Prometheus server; Grafana visualizes metrics, and Loki aggregates logs from the same nodes for correlated troubleshooting.

graph LR U[User / Client] --> GW[Application / Gateway Layer] GW --> CORE[HPC Resource Management & Mo Core Services] CORE --> DATA[(Data / Storage Layer)] CORE --> MON[Monitoring & Observability] MON --> ADMIN[Administrator]

Components

  • Node Exporter (per node system metrics)
  • DCGM Exporter (per-GPU telemetry)
  • Slurm Exporter (scheduler/queue state)
  • Prometheus (metrics storage/scraping)
  • Loki (log aggregation)
  • Grafana (dashboards and alerting)

Data Flow

Exporters expose metrics endpoints on each node → Prometheus scrapes them on an interval → Grafana queries Prometheus (and Loki for logs) to render dashboards → Alertmanager/Grafana alerting notifies administrators on threshold breaches.

Integration Architecture

Designed to sit alongside the Slurm cluster (Project 04) as its observability layer, and can share infrastructure with the AIOps platform (Project 03).

D. Technology Stack & Rationale

TechnologyWhy It Was Selected
PrometheusPull-based metrics collection well suited to dynamic HPC environments, with a powerful query language (PromQL) for analytics.
DCGM ExporterNVIDIA's own GPU telemetry exporter provides accurate utilization, memory, temperature and ECC error metrics not available from generic tools.
Slurm ExporterExposes scheduler-specific metrics (queue depth, job states, partition utilization) that generic system exporters cannot provide.
GrafanaFlexible dashboarding with strong Prometheus/Loki integration and built-in alerting.

E. Hardware Requirements

CPUModest dedicated server for the monitoring stack (4–8 cores sufficient for small-to-mid clusters).
GPUNone required for the monitoring server itself; exporters run on existing GPU compute nodes.
RAM16–32GB for Prometheus/Grafana/Loki depending on retention and cluster size.
StorageSSD storage sized to metric/log retention policy; long-term retention may require remote storage backends.
NetworkingStandard internal LAN access to scrape all cluster nodes.
Recommended ConfigurationSingle monitoring server adequate for clusters up to roughly a few hundred nodes; larger environments may need Prometheus federation.
Estimated, not tested: Storage sizing is an estimate dependent on metric cardinality and chosen retention window.

I. Testing & Validation

  • Metric accuracy test: compare exporter-reported values against manual checks (e.g. nvidia-smi vs DCGM exporter).
  • Alert test: trigger known threshold breaches and confirm notifications fire correctly.
  • Scale test: confirm scrape performance remains stable as node count grows.
  • Dashboard usability test: validate with actual administrators that key questions can be answered quickly.
