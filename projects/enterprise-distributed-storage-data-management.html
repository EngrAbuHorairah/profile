A. Project Overview

Problem Statement

Traditional single-controller storage arrays create both a capacity ceiling and a single point of failure, and organizations increasingly need to serve multiple access patterns (S3-style object storage for applications, block storage for VMs, file storage for general use) from one coherent platform.

Proposed Solution

A Ceph cluster providing RADOS as the underlying distributed object store, with CephFS (file), RBD (block) and S3-compatible object gateway access layered on top, replicated across multiple OSD nodes for durability, with ZFS used on individual nodes where local data integrity features are valuable.

Objectives

  • Deploy a distributed storage cluster supporting object, block and file access patterns.
  • Implement data replication/erasure coding for durability.
  • Provide per-user/project storage quotas.
  • Enable centralized, monitored, highly-available storage access.

Intended Users

IT infrastructure teams, application teams needing object/block storage, and general users needing shared file storage with quotas.

B. Business Value

Operational BenefitsConsolidates what might otherwise be several separate storage systems (NAS, SAN, object store) into one unified, centrally managed platform.
Cost OptimizationScales by adding commodity storage nodes rather than replacing an entire proprietary array at a capacity ceiling.
ProductivityApplication teams get self-service S3-compatible object storage without needing a separate cloud storage dependency.
ScalabilityDesigned from the ground up for horizontal scaling — capacity and performance grow by adding OSD nodes.
Security & ReliabilityPer-pool/user access controls and quotas prevent any single project from consuming all available capacity.
Organizational ImpactProvides the general-purpose storage foundation that complements the specialized parallel filesystem (Project 13) used for raw HPC I/O performance.

C. Technical Architecture

Architecture Overview

A Ceph cluster with monitor nodes (cluster state/quorum), OSD nodes (actual data storage across disks), and manager nodes, exposing RADOS Block Device (RBD) for block storage, CephFS for POSIX file access, and a RADOS Gateway for S3-compatible object storage.

graph LR U[User / Client] --> GW[Application / Gateway Layer] GW --> CORE[Enterprise Distributed Stora Core Services] CORE --> DATA[(Data / Storage Layer)] CORE --> MON[Monitoring & Observability] MON --> ADMIN[Administrator]

Components

  • Ceph Monitors (MON) for cluster quorum/state
  • Ceph OSDs (object storage daemons) across storage nodes
  • Ceph Manager (MGR) for cluster metrics/management
  • CephFS Metadata Servers (MDS) for file access
  • RADOS Gateway (RGW) for S3-compatible object access
  • ZFS on individual node-local storage where applicable

Data Flow

Client request (object/block/file) → routed to the appropriate Ceph access layer (RGW/RBD/CephFS) → RADOS distributes and replicates the underlying data objects across multiple OSD nodes according to the configured replication/erasure-coding policy → monitors maintain cluster map consistency throughout.

Integration Architecture

Can serve as the general-purpose storage backend for the AI platform's document store (Project 01), general file sharing, and VM/container block storage needs across the infrastructure.

D. Technology Stack & Rationale

TechnologyWhy It Was Selected
CephA mature, widely-deployed distributed storage system supporting object, block and file access from a single underlying cluster, avoiding the need for separate siloed storage systems.
RADOSThe reliable autonomic distributed object store underlying all of Ceph's access methods, providing self-healing replication/rebalancing.
S3-compatible Object GatewayGives application teams a familiar, widely-supported object storage API without dependency on a public cloud provider.
ZFSWhere used at the node level, provides strong local data integrity checks (checksumming) complementing Ceph's cluster-level replication.

E. Hardware Requirements

CPUModerate core counts per OSD node; Ceph performance scales with both CPU and disk I/O parallelism.
GPUNot applicable.
RAMSignificant RAM per OSD node (commonly 4–8GB per OSD daemon as a planning guideline) for cache and metadata performance.
StorageMultiple disks per OSD node (HDD for capacity tiers, SSD/NVMe for performance tiers or as a cache layer); total capacity planned with replication/erasure-coding overhead factored in.
Networking10GbE minimum between OSD nodes; 25GbE+ recommended for larger clusters to avoid replication traffic becoming a bottleneck.
Recommended ConfigurationMinimum viable production cluster: 3+ monitor nodes (odd number for quorum) and typically a minimum of several OSD nodes for meaningful redundancy.
Estimated, not tested: Exact sizing depends heavily on target capacity, replication factor and performance requirements; figures are general Ceph deployment guidance.

F. Software Architecture

Operating SystemLinux (Ubuntu Server or Rocky Linux, both well-supported by Ceph).
DependenciesCeph packages (ceph-mon, ceph-osd, ceph-mgr, ceph-mds, radosgw), cephadm or ceph-ansible for deployment
ServicesCeph Monitor, Ceph OSD, Ceph Manager, CephFS MDS, RADOS Gateway
DatabasesNot applicable in the traditional sense — Ceph maintains its own internal cluster map and metadata structures.
APIsS3-compatible REST API (via RGW) for object storage; standard POSIX for CephFS; block device interface for RBD.
MonitoringCeph's built-in dashboard plus Prometheus/Grafana integration for cluster health and capacity monitoring.
Automationcephadm for orchestrated deployment and lifecycle management of cluster daemons.

H. Security & Reliability

AuthenticationCeph's cephx authentication protocol for inter-daemon and client authentication; RGW integrates with standard S3-style access keys.
AuthorizationPer-pool and per-user capability restrictions limiting access scope.
Network SecuritySeparate public and cluster (replication) network segments recommended for performance and security isolation.
BackupCross-site replication or periodic snapshots/exports for disaster recovery beyond in-cluster redundancy.
MonitoringContinuous cluster health monitoring (OSD status, placement group health, capacity thresholds).
Disaster RecoveryDocumented procedures for OSD/node failure recovery and, where configured, multi-site disaster recovery.
High AvailabilityInherent high availability through replication/erasure coding and monitor quorum; no single node failure should cause data loss or unavailability when properly sized.

I. Testing & Validation

  • Durability test: simulate OSD/node failure and confirm automatic rebalancing/recovery without data loss.
  • Performance test: benchmark object/block/file I/O throughput against target workload profiles.
  • Quota test: verify per-project/user storage quotas are correctly enforced.
  • Failover test: validate monitor quorum behavior when a monitor node becomes unavailable.
Test scenarios describe planned validation criteria for this project's current status (Concept). No completed test results are claimed here.

J. Deliverables

K. Future Enhancements
